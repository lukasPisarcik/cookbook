feat: paginate the recipe list and bring Convex database I/O back inside the free tier

- **Four read-only queries were re-reading the entire 635-document recipe corpus on every call**, spending 71% of the monthly database-I/O allowance (733 MB of 1.03 GB against a 1 GB cap) on data that only changes when the importer runs. Convex bills whole documents with no projection, so `recipes.dietTags` paid 1,357 KB to return 53 bytes of diet tags — more than loading the entire shopping and pantry subsystem for both profiles combined. This was never a traffic problem: function calls sat at 11K of 1M.
- **`corpusMeta` now holds the four static aggregates**, one row per kind, computed by the importer — which already has every merged recipe in memory, so it costs no database I/O. `recipes.dietTags`, `pantry.knownIngredients` and `pantry.frequentIngredients` became single-row indexed reads, and `pantry.add` resolves an ingredient's product type from that row instead of scanning the corpus for one string match. The logic moved into a pure `computeCorpusAggregates()` in `src/lib/helpers/corpus.ts`, so this subsystem is unit-testable for the first time — including a regression test asserting the output equals what the old in-query loops produced.
- **`recipeCards` splits the card projection into its own thin table**, written transactionally by `seed.upsertRecipe` so the two tables cannot drift. The Recepty list only ever needed nine fields (~285 B per recipe) but was reading fat documents to get them, and because Convex invalidates a subscription when any table it touched changes, **toggling a single favourite re-read all 635 of them**. The search index moved to the card table and `recipes` kept only `by_slug` — the detail page is now its sole reader, and neither the category nor the search index is paid for twice.
- **The Recepty list is paginated at 20 rows with infinite scroll**, so first paint on a phone no longer waits on 635 rows — the sentinel loads the next page as it comes into view, with no „load more" button. Ordering moved onto a `searchText` index, because a page cannot be sorted across pages and an index on the raw `title` could only give UTF-8 byte order (which would put „Čokoládový" after „Zemiaky"); ordering on the diacritic-stripped title keeps the alphabetical order the list already had. Search results stay in relevance order. The diet-tag and favourites branches page in the handler rather than off an index, so they validate `paginationOpts.numItems` the way `.paginate()` does — without it a caller passing a negative value would have got most of the filtered set back in one page, on a function reachable with just the token.
- **`recipes.list` no longer reads `recipeState`** — favourites come from a separate `recipes.favoriteSlugs` query and are merged into the cards client-side. This is the change that actually fixed the favourite toggle: Convex invalidates a subscription when any table it touched changes, so while one handler read both tables, flipping one boolean re-read all 635 card rows. Pagination alone would have made this _worse_, not better — with N pages loaded, one toggle re-executed all N subscriptions.
- **`toggleFavorite` checks `recipeCards` rather than the fat `recipes` document** to confirm a recipe exists. Both tables are written in one transaction, so a card row exists exactly when its recipe does — but the fat read cost ~4.2 KB, which made the mutation the most expensive part of a favourite toggle once the card re-read was gone. Now measured at 0.3–0.6 KB.
- **The two filters Convex cannot index resolve a bounded slug list instead of scanning.** `dietTags` is an array field (no multi-key index) and favourites live in another table, so post-filtering a scan would have paid the full 188 KB to return a handful of rows. Diet tags are rare enough to precompute — 85% of the corpus carries none and the largest tag covers 62 dishes — so the importer writes a fourth `corpusMeta` row mapping tag → slugs (~3.2 KB for all four tags) and the filtered branch reads only those cards. Every filter still returns its complete matching set across pages rather than only the rows already loaded, and `category` became a filter field on the search index so combining search with a category stays one indexed read.
- **Špajza subscribes the 110 KB ingredient list only once two characters are typed** — the threshold its autocomplete already applied — so visits where nobody searches stop paying for it. Mid-word matching is unchanged („lej" still finds „olej").
- **Measured per interaction** from `usageStats.databaseReadBytes` on a live deployment, counting every query the interaction actually runs: opening the home tab 2,714 KB → **~7.5 KB**, toggling one favourite 1,357 KB → **~1.4 KB**, opening Špajza without typing 2,714 KB → **~9.5 KB**, filtering by a diet chip → **~24 KB** worst case at 62 matches. Two structural checks back this up: `recipes.list` no longer appears at all in the invalidation cascade after a favourite write, and no `recipes.list` execution ever reads more documents than one page holds. Projected monthly I/O falls from **1.03 GB to roughly 10 MB** — about 1% of the cap, though that projection depends on a usage mix rather than being directly measured. The earlier commits had left the home tab and a favourite toggle at 189 KB against a ≤120 KB target, because the card projection measures ~141 KB of payload plus 76 B/document of overhead at 635 recipes rather than the 90 KB originally estimated; splitting the read sets is what closed that gap.
- **The favourites filter grows with the number of favourites** — it reads every matching card at once, so roughly 5 KB at ten favourites and 27 KB at fifty. It is deliberately not capped: truncating would break the guarantee that a filter returns its complete matching set. Worth revisiting only if a profile ever approaches a few hundred favourites, where it would meet the full-scan cost it replaced.
- **The Dnes portion stepper is debounced** (~300 ms, optimistic locally), so holding `+` fires one `setCookingToday` mutation instead of one per tap — and each avoided mutation also avoids a `cookingToday` re-read. Switching kcal variant writes through immediately, carrying any pending multiplier and cancelling its timer, so the two controls can never fight over the row; a pending step is also flushed before the shopping list is generated and when leaving the page.
- **`bun tools/seed/import.ts --limit N [--prune]`** seeds a deterministic subset for dev deployments — the dev deployment was a second full corpus costing 190 MB/month by itself. `--prune` is required to actually shrink a deployment, since the importer only ever upserts. The subset pins the slugs the UI-proof gate hard-codes, then guarantees one recipe per diet tag before round-robining across categories, so every filter chip still has data at 40 recipes; the importer exits non-zero rather than silently dropping a fixture the gate depends on.
- **Infinite scroll on the Recepty list is the only user-visible change.** Everything else behaves as before: the „Časté" grid keeps its 40 tiles in the same order, the chips keep all four diet tags, and Špajza autocomplete still matches mid-word substrings (typing „lej" still suggests „olej") — which is why a Convex search index was rejected, as it matches token prefixes only.
- **Deploy ordering matters.** Two new `recipeCards` indexes and the new `corpusMeta` row have to be pushed and seeded _before_ the app deploys: a diet chip against a missing `dietTagSlugs` row returns an empty list with no error, which reads as „no vegan recipes" rather than as a fault. Re-run `bun tools/seed/import.ts` against production after pushing the schema.
